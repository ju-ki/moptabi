# No.225 フロント側のバリデーション強化

## 課題背景

- 共有型を作成して、ある程度型の不整合は減ったが、もしエラーが発生した時にあらかじめフロントエンド側でエラーを把握できるようにしたい
- プランニング後にスポット追加や削除、編集等を行うと移動時間等が不整合な状態になってしまって、そのままの状態で登録できてしまう

## 要件

### 目的

- プランニング後にスポット情報が変更された場合、移動時間や到着見込みなどの整合性が崩れた状態で保存されることを防止する。
- フロントエンド側で事前に不整合を検知し、ユーザーが「再プランニング」または「前回プランニング結果への復元」を行ってから保存できる状態にする。
- 既存で参照が残っている `spotRoutes` 関連を整理し、契約・実装・テーブル定義の不整合を解消する。

### スコープ

- 対象
	- プラン作成画面（`/plan/create`）の保存前バリデーション強化
	- プランニング後の編集（追加・削除・更新・並び替え）に伴う「再プランニング必要状態」の管理
	- 保存ボタンとは別導線での整合性解消アクション追加
	- `spotRoutes` の削除に伴う shared-types / backend / DB / テストの更新
- 非対象
	- 最寄駅情報の自動再計算（既存値を保持）
	- UIデザインの大幅な刷新
	- 新しいプランニングアルゴリズムの追加

## 機能要件

### FR-1: 再プランニング必要状態（dirty）の管理

- プランニング完了後、以下の操作を行った日付は「再プランニング必要状態」に遷移する。
	- スポットの追加
	- スポットの削除
	- スポット内容の編集（プランニングに影響がある項目のみ(メモの編集は除外する)）
	- スポットの並び替え
- 「再プランニング必要状態」は日付単位で管理する。
- 再プランニングを再実行して成功した日付は、再プランニング必要状態を解除する。

### FR-2: 保存前バリデーションの強化

- 保存実行時に、既存の必須チェック（タイトル、日付、スポット件数、文字数上限など）に加えて、再プランニング必要状態を検証する。
- 再プランニング必要状態の日付が1つでも存在する場合、保存APIの呼び出しをブロックする。
- ブロック時は、ユーザーが次に実施すべき操作（再プランニング実行または前回結果へ復元）を明示する。

### FR-3: 保存ボタンとは別導線での整合性解消

- プランニング後に、保存ボタンとは別に整合性解消アクションを表示する。
- 当該アクションは、変更有無にかかわらず押下可能とする。
- 押下時は、対象日付のスポット情報を「前回プランニング時点の結果」に復元する。
- 復元完了後、対象日付の再プランニング必要状態を解除する。

### FR-4: nearestStation の取り扱い

- スポット変更後も `nearestStation` は既存値を保持する（自動再計算しない）。
- 本課題では `nearestStation` の再探索/再算出は実施しない。

### FR-5: spotRoutes の削除

- 現行コードで参照されている `spotRoutes` について、以下から削除する。
	- shared-types のリクエストスキーマ
	- backend の入力スキーマ
	- backend の作成処理（`createTrip`）
	- DBスキーマ定義・relations
	- 関連テスト（schema / service / fixture）
- API設計書・関連ドキュメントの記述を更新する。

## 非機能要件

### NFR-1: データ整合性

- 不整合状態（再プランニング必要状態）では保存APIを呼ばないこと。
- 復元処理で前回プランニング時点の値へ戻ることをテストで保証すること。

### NFR-2: 可観測性・運用性

- 保存ブロック時の理由をユーザーに分かる文言で表示すること。
- エラーメッセージは日付単位で識別可能にし、原因追跡しやすくすること。

### NFR-3: 性能

- dirty判定・保存前チェック追加により、通常の編集操作で体感遅延を発生させないこと。
- 復元処理は対象日付のみ更新し、不要な全体再描画を避けること。

### NFR-4: テスト容易性

- store単体テストで dirty 付与/解除/復元を検証可能な構造にすること。
- コンポーネントテストで保存ブロックと別導線アクションを検証可能にすること。

## 受け入れ条件

1. プランニング後にスポットを1件でも編集した場合、保存時にブロックされる。
2. ブロック時に、再プランニングまたは復元操作への導線が表示される。
3. 復元操作で前回プランニング時点へ戻り、その日付は保存可能状態になる。
4. 変更がない日付は従来どおり保存できる。
5. `spotRoutes` を含まない契約で作成APIが通る。
6. 既存の上限チェック（プラン数・日数・1日スポット数）は維持される。

## 影響範囲

- frontend
	- store管理（dirty, snapshot, restore）
	- 保存前バリデーション
	- 別導線UI
- shared-types
	- Trip作成スキーマ（`spotRoutes` 削除）
- backend
	- Trip入力スキーマ
	- createTrip保存処理
	- DBスキーマ/relations
	- テスト
- docs
	- API設計書
	- plan-create仕様

## 確定事項

1. 旧クライアント互換方針
	- `spotRoutes` を含む旧payloadは、`spotRoutes` を無視して受理する。
2. 復元対象の範囲
	- 「前回プランニング時点へ戻す」の復元対象はスポット情報のみとする。
3. 保存ブロックメッセージ
	- 文言は要件定義書で固定する。

### 保存ブロック文言（固定）

- タイトル: プランニング結果が最新ではありません
- 本文: スポット内容が変更されたため、このままでは保存できません。再プランニングを実行するか、前回のプランニング結果に戻してください。
