# No.202 staging環境でのプレビュー機能

関連資料:
* 詳細な実装計画は `docs/tasks/No.202_実装計画.md` を参照

## 背景

* 現状、本番環境中心の動作確認になっており、検証時のリスクが高い。
* 特にDB定義変更を含む改修では、本番影響の可能性がある。

## 目的（ゴール）

1. PR単位で安全に確認できるプレビュー導線を整備する。
2. 本番影響を避けた状態で、frontend / backend の結合動作を確認できるようにする。

## スコープ

1. frontend（Cloudflare Pages）のプレビュー公開
2. backend（Cloudflare Workers）のプレビュー公開
3. PRへのプレビューURL通知とデプロイ結果の可視化

## スコープ外

1. PRごとのNeon DB分離（今回は実施しない）
2. shared_types の単体デプロイ

## 前提

1. frontend: Cloudflare Pages
2. backend: Cloudflare Workers
3. DB: Neon（staging固定DBを使用）
4. shared_types: 未デプロイ（CI内ビルドで吸収）

## 要求事項

### 機能要件

1. トリガー
	* baseがdevのPR（open / synchronize / reopen）で、プレビュー用デプロイ処理を実行する。
2. frontendプレビュー
	* PRごとにアクセス可能なプレビューURLを払い出す。
3. backendプレビュー
	* PRごとの変更内容でbackendをデプロイし、frontendプレビューから疎通できる状態にする。
4. PR可視化
	* PRコメントにプレビューURLを自動投稿または更新する。
	* PRチェック（GitHub Checks）でデプロイ成功/失敗が分かる状態にする。
5. 並列確認
	* staging固定DBを前提に、複数PRの並列確認を許容する。
	* 並列確認時は、データ衝突を避けるため本ドキュメントの運用ルールに従う。
	* ただしDBマイグレーションを含むPRは同時適用せず、CI/CD上の排他ロックで1件ずつ順次実行する。

### 非機能要件

1. 安全性
	* 本番用Secretは利用しない。
	* staging専用Secretを使用し、本番と分離する。
2. 運用性
	* 同一PRで再実行時はコメントを追記ではなく更新し、情報を1箇所に集約する。
3. 追跡性
	* PR上で「どのコミットのプレビューか」が識別できること（最低限SHAを確認可能にする）。

## 受け入れ条件（Definition of Done）

1. base=devのPR作成/更新時に、frontendとbackendのプレビューが自動作成される。
2. PR上で以下が確認できる。
	* frontendプレビューURL
	* backendエンドポイント（または疎通済み表示）
	* デプロイ成否
3. 同一PRで再実行した場合、同じURLを更新し続ける。
4. PR close / merge後も環境を残す前提で運用できる。
5. 本番用Secretを参照していないことをWorkflow設定で確認できる。
6. DBマイグレーションを含むPRは、CI/CD上の排他ロックにより1件ずつ順次確認・適用される。
7. PR作成時に、同一ブランチ群でマイグレーションPRが複数ある場合は自動で警告が通知される。
8. マイグレーション実行時に、PR番号・実行時刻・コミットSHAが自動記録される。
9. マイグレーション失敗時に、自動ロールバック（トランザクションロールバックまたはバックアップ復元）が実行される。

## 実装方針メモ

1. 既存のCI（frontend/backend）とは責務を分離し、stagingプレビュー用ジョブ（またはworkflow）を追加する。
2. 環境変数はstaging用の命名に統一し、previewという環境名は使わない。
3. 環境名はstagingで統一しつつ、デプロイURLはPR単位で払い出す。
4. DBはstaging固定のため、本ドキュメントの「DB安全運用ルール」に従って運用する。

## DB安全運用ルール（staging固定）

### 1. 書き込み制限

1. 目的
	* プレビュー確認時の意図しない更新・削除からstagingデータを保護する。
2. 運用ルール
	* 既定は「読み取り中心」の確認とし、更新系操作は必要最小限に限定する。
	* 危険操作（大量更新・一括削除・スキーマ破壊的変更）は、PR確認中に直接実行しない。
	* 破壊的な検証が必要な場合は、メンテナ承認後に時間帯を決めて実施する。
	* API側で可能な範囲でガードを実装する（例: 管理APIの無効化、対象件数上限）。
	* 並列確認時の書き込みデータは、PR番号など識別子をキーにして作成し、相互に上書きしない。

### 2. データ保護

1. 目的
	* staging固定DBを複数PRで共有しても、復旧可能性と追跡性を確保する。
2. 運用ルール
	* マイグレーション前にバックアップ（または復元可能なスナップショット）を取得する。
	* スナップショット取得時刻、実行者、対象PR番号を運用ログに記録する。
	* 個人情報や機微情報はstagingに持ち込まない。必要時はマスキング済みデータを使用する。
	* データ更新を伴うE2E確認は、専用テストデータ（識別しやすいプレフィックス）で実施する。
	* DBマイグレーションを伴うPRが複数ある場合、CI/CDで排他ロックを取得したPRのみ適用し、同時適用を禁止する。
	* PR作成時に、同一ブランチ群でマイグレーションPRが複数存在する場合は自動検出してPRコメントまたはChecksで警告する。
	* マイグレーション実行時は、PR番号・実行時刻・コミットSHAをCI/CDから自動で運用ログへ記録する。
	* マイグレーション失敗時は、自動でトランザクションロールバック、または事前バックアップからの復元を実行する。
	* 例外対応として手動判断が必要な場合でも、基本ルールは「マイグレーションを含むPRは1つずつ順次確認」とする。
	* PR close / merge後に環境は残るため、不要になったテストデータは定期的に棚卸しして手動で削除する。

### 3. ロールバック手順

1. 失敗検知
	* デプロイ失敗、想定外エラー増加、主要機能の疎通失敗をロールバック判断条件とする。
2. 手順
	* 直前の安定リビジョンへfrontend/backendを再デプロイする。
	* DB変更が原因の場合は、取得済みスナップショットからstaging DBを復元する。
	* 復旧後に最低限のスモークテスト（ログイン、主要API、画面表示）を実施する。
	* PRコメントに「ロールバック実施」「影響範囲」「次アクション」を記載する。
3. 完了条件
	* 主要機能の疎通が回復し、エラー率が通常範囲に戻っていること。
	* 関係者に復旧連絡が完了していること。

## 今回の確認結果（2026-04-16）

1. プレビュー対象: frontend + backend（DBはstaging固定）
2. トリガー: staging向け運用を目的としつつ、実運用上はbase=devのPRで起動
3. ライフサイクル: PR close / merge後も環境は残し、自動削除はしない
4. PR運用: URL自動投稿、デプロイ結果のチェック表示
5. セキュリティ: 本番影響を避けるため、Secretを分離
6. 環境変数方針: previewという環境名は使わず、stagingで統一
7. staging運用: 複数PRの並列確認を許容
8. デプロイURL: PR単位で払い出す
