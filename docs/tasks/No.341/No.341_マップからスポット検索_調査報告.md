# No.341 マップからスポットを検索できるようにする 調査報告

- Issue: https://github.com/ju-ki/moptabi/issues/341 （関連: #339 / PR #410）
- 調査日: 2026-10-14
- 対象ブランチ: `dev`（ac8788b 時点）

## 1. 要件整理

### 目的
- テーマ/キーワード中心の「フィルター検索」とは別に、地図を見ながら視覚的にスポットを探せるようにする。
- フィルター検索は結果が絞られすぎて「めぼしいスポットが出てこない」ことがあるため、地図上で周辺を眺めて選べる導線を用意する。

### 要件（Issue 記載）
1. フィルター検索とは別に、マップから検索できる。
2. 地図の中心点は #339 で追加したプランの地点（出発地・目的地・登録済みスポット）を基準に選べる。
3. 中心点は手で編集（移動）できる。
4. 旅行中の利用も考えて、現在地も中心点として選べる。

### 背景・制約
- 以前は同様の機能があったが、Places API の呼び出し回数が多くなる懸念で削除済み（Issue 本文より。現リポジトリの履歴は squash されており、旧実装の該当コミットは特定できなかった）。
- 収益化方針として「コストが重い Google Maps API の呼び出しは抑える」前提があるため、**呼び出し回数の制御が実質的な主要件**になる。

### 確認事項と決定（PR #445 レビュー、2026-10-14）

| Q2 | 地図を動かしたら自動で検索するか | しない。地図上のピンをクリックして追加する |

## 3. 実現案

共通の前提: 中心点の決め方（プランの地点 / 現在地）は #339 の `planPoints` ロジックを再利用する。そのために `GoogleSpotSearch.tsx:82-113` を `hooks/spot-search/use-search-center.ts`（仮）へ切り出す。

### 案A: 既存の検索結果マップを拡張する
`SearchResultsView` の地図に「このエリアで検索」ボタンと POI タップでの追加を足す。

- 変更範囲: `SearchResultsView.tsx`, `GoogleSpotSearch.tsx`, `lib/plan.ts`（POI 詳細取得関数を追加）
- メリット: 新規画面が不要で工数が小さい。
- デメリット: 一度フィルター検索しないと地図が出ない（初期表示がリスト）ため、「フィルター検索とは別に」という要件を満たしにくい。`SearchResultsView` は行きたいリスト・過去スポットでも共有しており、Google 専用の処理が混ざる。
- 工数感: 小（1〜2日）

### 案B: 「地図から探す」タブを新設する（推奨）
`SpotSelectionDialog` に4つ目のタブ `MapSpotSearch` を追加。地図を主役にした検索画面にする。

画面の流れ（レビュー反映後）:
1. タブを開くと、基準地点（既定は出発地、なければ東京駅）を中心に地図を表示。プランの地点（出発地・目的地・登録スポット）はバッジで切替、現在地はボタン押下時に取得。この時点では **Places API を呼ばない**（地図の表示のみ）。
2. 地図上には既にプランに入っているスポットと、出発地・目的地をマーカー表示（API 呼び出しなし）。
3. **Google 標準の POI ピンをクリック** → `placeId` から `Place.fetchFields` で詳細を1件だけ取得し、InfoWindow に「計画に追加」ボタンを出す。クリックした分だけ課金されるので呼び出しが最小。追加済みのスポットは「選択解除」に切り替える。
4. 中心点は「候補から選んで地図をジャンプ」＋「地図を動かして微調整」で決める。候補は 6-3 を参照（現在地が東京で旅行先が北海道のような場合も、ドラッグせずに移動できるようにする）。
5. エリア検索（Nearby Search）・テーマチップ・キーワードは地図タブに置かない（Google検索タブで行う）。

- 変更範囲:
  - 新規: `components/spot-selection/MapSpotSearch.tsx`, `hooks/spot-search/use-search-center.ts`, （POI 詳細取得は既存の `lib/place-fetcher.ts:130` `fetchPlaceDetailsWithRetry` を再利用するため新規関数は不要。7-1 参照）
  - 更新: `SpotSelectionDialog.tsx`（タブ追加、`grid-cols-4`）, `GoogleSpotSearch.tsx`（中心点ロジックをフックに置き換え）, `spotSearchStore.ts`（未使用の `mapCenter` / `mapSelectOpen` を整理し、地図用の状態を追加）
  - テスト: `tests/components/spot-selection/MapSpotSearch.spec.tsx`, `tests/hooks/use-search-center.spec.ts`, `tests/lib/geo.spec.ts` 拡張
  - バックエンド・DB の変更なし
- メリット:
  - 要件「フィルター検索とは別に」「プランの地点/現在地を基準」「中心を編集」をすべて満たす。
  - 自動検索をせず、呼び出しは「POI クリック1回=1件」だけなので、以前の「呼び出しが多すぎる」問題を避けられる。
  - テーマ絞り込みで結果が消える問題を、POI タップ（Google が地図に出しているものをそのまま選べる）で回避できる。
- デメリット:
  - タブが4つになり、スマホでタブ文言が窮屈になる（アイコン＋短い文言にする必要あり）。
  - ダイアログ内で地図を高さいっぱいに使うレイアウト調整が必要（`DialogContent` が `max-h-[90vh] overflow-y-auto`）。
  - POI タップは Google 標準アイコンに依存するため、表示される POI の種類は制御できない。
- 工数感: 中（3〜4日、テスト込み）

### 案C: 地図を動かすたびに自動で検索する
`onIdle` で表示範囲が変わるたびに `searchNearby` を呼ぶ（デバウンス付き）。

- 変更範囲: 案Bとほぼ同じ
- メリット: 操作が最も直感的。
- デメリット: 地図を少し動かすたびに呼び出しが発生し、Issue 背景にある「呼び出し回数が多い」問題がそのまま再発する。デバウンスやキャッシュを入れても回数の上限が読めない。
- 工数感: 中（3日）＋コスト監視の仕組みが別途必要

| API 呼び出し | 少 | 少（操作に比例） | 多（読めない） |

### 推奨: 案B
- 要件をすべて満たしつつ、削除理由だった API 呼び出し回数を「ユーザーが押した分だけ」に抑えられる。
- POI タップによる追加は、地図に表示されている場所をそのまま選べるので、フィルター検索の精度に左右されない。
- 中心点ロジックをフックに切り出すことで、Google検索タブと地図タブで同じ基準地点を共有でき、#339 の資産をそのまま活かせる。

### 案Bの実装上の注意
- POI タップの `placeId` 取得は `GoogleMap` の `onClick` イベント（`google.maps.IconMouseEvent`）で `e.placeId` を見て、`e.stop()` で Google 標準の InfoWindow を抑止する。
- POI 詳細取得の fields は、カード表示に必要な最小限に絞る（`editorialSummary` 等の高い区分の fields は外す検討）。
- 同じ POI を続けてクリックしたときは、取得済みの詳細を使い回して再取得しない。
- 地図表示自体も Maps JavaScript API の地図読み込みとして課金対象になるため、タブを開くまで `GoogleMap` をマウントしない（Radix Tabs の非アクティブタブは既定でアンマウントされるのでそのままでよい）。
- 現在地は「現在地」ボタン押下時にのみ取得する（地図タブ内の話。Google検索タブ側の P-1 は今回対象外）。

## 4. 追加の提案

調査中に気づいた関連改善と、#341 と相性の良い機能案です。

### 不具合・改善（小さめ）
> レビュー結果: **P-5・P-6 は #341 で対応する**。P-1〜P-4 は今回対象外（P-3 は Q4 の決定により実施しない）。

- **P-1. 現在地の取得をボタン押下時に変更**: `GoogleSpotSearch.tsx:76` でダイアログを開くたびに位置情報を要求している。プランの地点だけ使う人にも許可ダイアログが出るため、`useCurrentLocation` に `request()` を持たせて明示的に取得する形にする。
- **P-2. 検索結果マップの中心を検索中心にする**: `SearchResultsView.tsx:30-34` は結果の先頭を中心にしており、0件だと東京駅が出る。`center` を props で受け取れるようにする。
- **P-3. 検索回数の見える化と上限**: Places API はフロントから直接呼んでおり、回数を把握できない。まずはフロントで1セッションあたりの検索回数を数えて上限（例: 30回）を設け、将来の有料枠（赤字防止の課金基盤）につなげられるようにする。
- **P-4. 未使用 state の整理**: `spotSearchStore.ts` の `mapCenter` / `mapSelectOpen` / `setMapCenter` / `setMapSelectOpen` は未使用。案Bで地図用 state を追加する際にまとめて整理する。
- **P-5. `planSpotSelection` の日付ごとのリセット**: 別日のダイアログを開いても前日の選択が残るため、ダイアログを開いたとき（または `date` 変化時）に `clearPlanSpotSelection` する。
- **P-6. 検索半径の円を控えめに**: `LocationAdjustModal.tsx:16-28` の円が赤・不透明度0.35で POI が見えにくい。枠線のみ＋薄い塗りにする。

### 機能案（#341 と相性が良いもの）
> レビュー結果: いずれも #341 の対象外。
> - F-1: ダイアログ全体のレイアウト見直し（「リストで探す」と「地図で探す」の2段構成）と合わせて **#341 で対応する**（レイアウト案は 6章）。
> - F-2: 規模が膨らむため見送り。
> - F-3: 将来のレコメンド機能（ナレッジが溜まったらおすすめスポットとして出す）として検討。

- **F-1. 行きたいリストを地図に重ねる**: 地図タブで、行きたいリストのスポットを別色ピンで常時表示する。DB のデータなので API 費用ゼロで、「近くに行きたい場所があった」に気づける。コンセプトの「旅行前（計画）」と行きたいリストをつなぐ導線になる。
- **F-2. ルート沿いで探す**: 出発地→目的地（または隣り合うスポット間）の経路に沿って検索する。Places API (New) の `searchAlongRoute` 相当、または経路上の数点で Nearby Search。移動の途中で寄り道したい日帰り・週末旅のターゲットに合う。
- **F-3. 「今ここから行ける」検索（旅行中向け）**: 現在地＋次の予定までの空き時間から、徒歩◯分圏内のスポットだけを出す。#341 の「旅の間も現在地」と組み合わせて、プラン詳細画面からも地図タブを開けるようにする。
- **F-4. 検索結果のキャッシュ**: 同じ中心（小数点3桁程度で丸める）・半径・テーマでの検索結果をセッション中は使い回し、タブの往復や再検索での呼び出しを減らす。

## 6. レイアウト案（PR #445 レビューで追加）

> 2026-10-16 のレビューで、都道府県での移動は住所入力に置き換え、距離は今の中心点からに決定した。最終的な内容は [No.341_実装計画.md](./No.341_実装計画.md) とモック（https://claude.ai/artifact/MQ3kafiopuQxY9mUh5RCWC）を正とする。

### 6-1. 全体構成
スポット追加ダイアログ（`SpotSelectionDialog`）を「探し方」で2段に分ける。

```
[ リストで探す | 地図で探す ]            ← 1段目（セグメント切替）
  └ リストで探す: [ Google検索 | 行きたいリスト | 過去のスポット ]  ← 2段目（既存3タブをそのまま）
  └ 地図で探す : 地図＋中心点の候補＋ピン（POI / 行きたいリスト / 過去 / プラン）
```

- 「リストで探す」は既存の `GoogleSpotSearch` / `WishlistSpotSearch` / `VisitedSpotSearch` をそのまま入れる（中身は変えない）。
- 「地図で探す」は新規 `MapSpotSearch`。行きたいリストと過去のスポットは「条件で絞り込む」のがリスト側、「場所で眺める」のが地図側、と役割を分けるので重複にならない。
- 最後に使った探し方（リスト/地図）は `spotSearchStore` に保持し、次に開いたときもその表示にする。

### 6-2. 地図で探す（PC）

### 6-3. 中心点の候補
地図をドラッグで長距離移動しなくて済むように、候補チップから一発で移動できるようにする。上から優先度順。

| 候補 | データ元 | API 費用 |
|---|---|---|
| 出発地・目的地 | `currentPlan.departure` / `destination` | なし |
| その日に登録済みのスポット | `currentPlan.spots` | なし |
| 他の日に登録済みのスポット | `plans[].spots`（複数日のプラン向け） | なし |
| 現在地 | `useCurrentLocation`（ボタン押下時に取得） | なし |
| 都道府県の中心 | `data/constants.ts:436` の `prefectureCenters`（既存、行きたいリストのエリア検索で使用中）。目的地の都道府県を初期選択にする | なし |

- 初期中心は「目的地 → 出発地 → 目的地の都道府県 → 東京駅」の順で最初に取れたもの。
- 候補を選んだら地図を移動するだけで、検索 API は呼ばない。
- 地名の自由入力（Places Autocomplete）は課金が発生するため今回は入れない。

### 6-4. ピンの種類

| ピン | 見た目 | クリック時 | API 費用 |
|---|---|---|---|
| 出発地・目的地 | S / G のラベル付き | 何もしない | なし |
| プランに追加済みのスポット | 訪問順の番号付き（青） | カード表示、「選択解除」 | なし |

- 行きたいリスト・過去のスポットは既存の取得処理（`WishlistSpotSearch` / `VisitedSpotSearch` が使うフック）を再利用し、絞り込みは行わず全件をピン表示する。

## 7. #158（営業時間の制御）・ユーザー別上限を踏まえたブラッシュアップ（2026-10-16 追記）

dev に入った #158（PR #437 ほか）と、ユーザー別の上限（`useUserLimits`）を前提に、地図で探す・2段構成の設計を見直した。

### 7-1. POI クリック時の詳細取得は既存の取得処理を使う
- `lib/place-fetcher.ts:130` の `fetchPlaceDetailsWithRetry(placeId)` が既にあり、セッション中のメモリキャッシュ、3回リトライ、緯度経度の localStorage キャッシュ（規約上許される30日）を持っている。
- 取得 fields（`lib/google-maps.ts:88` `PLACE_DETAIL_FIELDS`）に #158 で `businessStatus` が追加され、戻り値に `openingPeriods` / `businessStatus` が入る。
- 地図で探すの POI クリックはこれをそのまま使う。同じ POI を何度押しても2回目以降は API を呼ばない。取得処理を新しく作る必要はない（`fetchPlaceById` も `lib/google-maps.ts:105` に既にある）。

### 7-2. 選択中のスポットカードに計画日の営業状況を出す
- カードに `SpotOpeningSummary`（`components/common/OpeningHoursInfo.tsx:92`）を `planDate` 付きで置き、「定休日」「臨時休業」「閉業」と計画日の営業時間を表示する。祝日は判定しないため `HolidayNote` も添える。
- 地図の上部（PC は左パネル上部）に「計画日: 10/18(土)」を出し、どの日の営業状況かを分かるようにする（`getWeekdayLabel` を使う）。
- 定休日などでも追加は止めない（#158 の方針と同じ）。追加後のトーストは 7-3 の仕組みでそのまま出る。

### 7-3. 追加は必ず `SpotSelectionDialog` の `handleSpotSelect` を通す
- `SpotSelectionDialog.tsx:54` の `handleSpotSelect` に、ユーザー別上限のチェック（上限取得失敗時は追加を止める）と、定休日などの確認トースト（`:85`）が入った。
- `MapSpotSearch` も他のタブと同じく `onSpotSelect` props で受け取り、独自に `setSpots` を呼ばない。開始時刻は `GoogleSpotSearch` と同じく `setStartTimeAutomatically` で入れる。
- 上限に達しているときは、カードの「計画に追加」を押せない状態にして理由を出す（押してからトーストで弾かれるより分かりやすい）。

### 7-4. 行きたいリスト・過去のスポットのピンは無料ではない（6-4 の訂正）
- `useWishlistSpots` / `useVisitedSpots` は、DB から取った各スポットについて `fetchPlaceDetailsWithRetry` で詳細を取っている（`hooks/spot-search/use-wishlist-spots.ts` 内の `Promise.all`）。ピン表示にも同じ取得が必要になる。
- 費用を抑えるため次のようにする。
  - ピンの表示切替は**初期 OFF**。ON にしたときだけ取得する。
  - リストで探すの各タブと同じフックを使うので、既にリスト側で開いていればメモリキャッシュに乗っていて追加の呼び出しはない。
  - 行きたいリストの件数はユーザー別上限（既定 20 件）までなので、最大でもその件数分で止まる。
- 6-3 の「API 費用なし」は出発地・目的地・登録スポット・現在地・都道府県の候補には当てはまる（いずれもプランのデータか定数）。

### 7-5. 「計画日に営業しているスポットのみ」フィルターの置き場所
- 今は `OpenOnPlanDateFilter` が3タブそれぞれに置かれている（`GoogleSpotSearch.tsx:325`, `WishlistSpotSearch.tsx:153`, `VisitedSpotSearch.tsx:185`）。状態はストアで共有済み。
- 2段構成にするときは、「リストで探す」の2段目タブの上に1か所だけ置く形にまとめる。地図で探すでは、ON のときに行きたいリスト・過去のスポットのピンから計画日に休みのものを隠す（`isOpenOnPlanDate` を使う）。Google 標準の POI はアプリ側で描画していないので隠せない（クリック後のカードで分かる）。

### 7-6. ピンで営業状況を見分ける
- 行きたいリスト・過去のスポットのピンは、計画日に休み（`hasOpeningWarning` が true）のとき薄く表示する。フィルターを OFF にしていても一目で分かる。
- プランに追加済みのスポットは、滞在時間が営業時間外（`OUTSIDE_HOURS`）なら番号ピンに警告の印を付ける。プランニング画面の警告（#158）と同じ判定を使う。
